# Accessibility Review — Memory Lane & Voyage History (Story 6.2)

## Overall verdict

The four new surfaces (Memory Lane Reveal deck, shareable group card, Voyage History, Persistent Journey Screen) carry forward Wayfinder's established accessibility conventions in places — the deck's VoiceOver announcement spec and the marker-peek-card-style hit-slop pattern are good precedents — but the new full-bleed "aurora" background and two of the four new screens were not run through the same rigor as the rest of the system. Two concrete WCAG AA contrast failures ship in the authoritative mockups with no documented floor or exception, the deck's only documented navigation method is a path-based swipe gesture with no button/tap-zone fallback, and Voyage History / the Persistent Journey Screen introduce animation and sub-44pt controls that never made it into Motion & Transitions, the Reduce Motion enumeration, or the Accessibility Floor's screen-reader notes at all.

### Findings

- **critical** Text rendered directly on `memory-lane-aurora` (no `memory-lane-card` panel underneath) can fall well below WCAG AA. Computed contrast of `ink-secondary` (#667085) against the blended aurora ranges from ~3.85:1 (single blob overlap) down to ~2.67:1 (multi-blob overlap zones, e.g. the trigger screen where 3-4 circles stack), both under the 4.5:1 normal-text floor. `ink-primary` headlines stay safe (~9.5:1 even in worst-case overlap) but body/caption copy set in `ink-secondary` directly on the aurora does not. (DESIGN.md lines 377–393, `memory-lane-aurora` token — no contrast floor/assumption documented, unlike `button-ignition` and `marker-peek-card`'s `statPair` which both carry documented near-miss notes; mockups/key-memory-lane-reveal.html lines 78–80, 96–98, 213 — subheads set directly on aurora with no panel). *Fix:* require `ink-secondary`/caption text to always sit inside a `memory-lane-card` panel (never directly on raw aurora), or cap combined blob opacity under text-only regions and document the resulting floor the way `button-ignition`'s near-miss is documented.

- **critical** `ink-disabled` (#98A2B3) is reused as the caption-label color for "Duration"/"Distance"/"Stops" stat labels inside white `memory-lane-card`/`content-panel` panels across three new mockups. Against pure white this measures ~2.58:1 — far under the 4.5:1 AA floor for normal text (these captions run 9–9.5px). DESIGN.md's one existing documented near-miss for this card family (`statPair`'s `accent-teal`/`warning` numeral colors, DESIGN.md lines 260–270) only covers the numeral color, not this caption gray, so there is no existing exception that covers it. (mockups/key-memory-lane-reveal.html lines 189–190 (finale card); key-memory-lane-share-card.html lines 80–81; key-journey-screen.html lines 91–93). *Fix:* darken these caption labels to at least `ink-secondary` (#667085, ~4.97:1 on white) or document an explicit reviewed exception.

- **high** Swipe is the *only* documented way to move through the Memory Lane deck. EXPERIENCE.md's `memory-lane-deck` component row and its "End Voyage → Memory Lane Reveal" Motion & Transitions write-up describe horizontal drag/swipe exclusively; no button, chevron, or tap-zone alternative is specified anywhere, despite Interaction Primitives establishing Tap as "the only primitive required anywhere in the core loop" for the rest of the product. A chevron/arrow-key fallback was actually prototyped (`.working/direction-memory-lane-b-player-constellation-INTERACTIVE.html`) but was explicitly declined and set aside per `.memlog.md` entries 95–96, with nothing substituted back in. (EXPERIENCE.md lines 112, 148, 174; .memlog.md lines 95–96). *Fix:* reinstate a minimal non-gestural advance/retreat control (tap-left/tap-right zones or small chevrons) so the deck satisfies WCAG 2.5.1 (path-based gesture functionality must also be operable via a single pointer without a path-based gesture).

- **high** Two of the four new screens ship animation with zero Motion & Transitions coverage and zero Reduce Motion coverage. The Persistent Journey Screen's replay-hero play icon has a continuous 2.4s looping opacity pulse (`@keyframes shimmer`, key-journey-screen.html lines 39, 79) that appears nowhere in EXPERIENCE.md. Voyage History's list rows have a staggered entrance (`@keyframes rowIn`, key-voyage-history.html lines 41, 50, 77–81) and its empty state reuses `fadeUp` plus the continuous orbit loop (lines 40, 42, 92–104) — also undocumented. Neither screen has a Motion & Transitions subsection, and neither is named in the Accessibility Floor's Reduce Motion bullet (EXPERIENCE.md line 193), which otherwise exhaustively enumerates every other animation in the system by name. (EXPERIENCE.md lines 156–199 — no "Voyage History" or "Persistent Journey Screen" subsection exists). *Fix:* add Motion & Transitions subsections for both screens and add their animations by name to the Reduce Motion enumeration.

- **high** Touch targets under the documented 44pt(iOS)/48dp(Android) floor. The Persistent Journey Screen's `back-chip` (back arrow) and overflow (`⋯`) icon buttons render at 34×34px (key-journey-screen.html lines 42, 65, 67) with no hit-slop padding documented — unlike the established visual-vs-hit-region pattern already used for `map-marker` and marker-peek-card's copy/Get-Directions controls (EXPERIENCE.md line 195). The same screen's "Share the card"/"Share the video" buttons compute to roughly 41–42px tall (line 98–99: ~11–13px vertical padding + ~13px font/line-height), under the "Tap targets ≥ 44pt / 48dp everywhere" rule (EXPERIENCE.md line 196). *Fix:* pad `back-chip`/overflow to a 44×44 (iOS)/48×48 (Android) hit region via invisible hit-slop, and add ~2–3px more vertical padding to both share buttons.

- **medium** No Memory Lane graphical element is explicitly marked decorative/excluded from the accessibility tree anywhere in either spine document. The aurora blobs, the trigger/empty-state orbiting dots, the progress dots, spark bursts, the superlatives crown emoji, and the closing-beat dashed ring have no such note — unlike `horizon-strip` and `home-journey`, which both explicitly state "Purely decorative — no tap target" (DESIGN.md lines 597, 599). The 2026-08-11 Accessibility Floor addition (EXPERIENCE.md line 194) specifies what a screen reader *announces for card content* but says nothing about suppressing the surrounding graphical decoration from being individually announced as unlabeled shapes/images. (DESIGN.md lines 377–393, 607). *Fix:* add an explicit "purely decorative / aria-hidden" note to `memory-lane-aurora` and the deck's progress dots, matching the `horizon-strip`/`home-journey` precedent.

- **medium** The continuous "orbit" animation (the trigger screen's three orbiting dots, reused on Voyage History's empty state per DESIGN.md line 454) is not named in the Reduce Motion enumeration (EXPERIENCE.md line 193), even though every other continuous ambient loop in the system (`horizon-strip` drift, `home-journey`'s road/dot-bob/glow/sparks) is explicitly named there. (mockups/key-memory-lane-reveal.html lines 33, 74–76; key-voyage-history.html lines 42, 98–100). *Fix:* add the orbit loop by name to the Reduce Motion bullet.

- **medium** Some per-card entrance animations actually used in the mockup aren't literally named in EXPERIENCE.md's card-entrance description (line 174), which enumerates only `dotPop`/`fadeUp`/`fillBar` by name: `converge` (the Destination card's dots flying inward, key-memory-lane-reveal.html lines 34, 93–95) and `crownDrop` (the Superlatives card's crown-emoji drop, lines 39, 158). Likely intended to be covered by the umbrella phrase "per-element entrance choreography," but the doc's own convention elsewhere is to name every distinct animation curve. *Fix:* fold `converge` and `crownDrop` into the named list, or state explicitly that the umbrella term covers any other card-specific entrance animation.

- **medium** No documented focus-order/focus-move behavior for the swipeable deck. EXPERIENCE.md's Accessibility Floor (line 194) specifies what VoiceOver/TalkBack *announces* when a card becomes active but never states whether keyboard/switch-control focus actually moves onto the new card's content, versus an announcement firing via a live region while focus stays put — a real behavioral difference for anyone navigating linearly. The general rule that "Focus/reading order on every surface... matches visual order" (line 199) doesn't specifically address the deck's one-screen-at-a-time swap. *Fix:* add one sentence stating whether focus programmatically moves to the new card's heading on activation.

- **medium** Voyage History (list rows, search field, empty-state CTA) has no VoiceOver/TalkBack notes at all, despite being a brand-new v1.1 screen. Unlike the Memory Lane deck and marker-peek-card, which both got dedicated Accessibility Floor bullets, there is no line describing what a `voyage-history-row` announces (e.g. "Big Sur, 214 miles, August 11, 3 voyagers, button"), whether the search field has an accessible label beyond its placeholder text, or any framing for the empty state's CTA. (EXPERIENCE.md lines 187–199; DESIGN.md lines 441–455). *Fix:* add a Voyage History bullet to the Accessibility Floor analogous to the Memory Lane deck one.

- **low** The Voyage History search field's placeholder text ("Search by destination") is set in `ink-disabled` (#98A2B3) at ~2.4:1 against its own field background — reusing the semantically "disabled" ink token as the only visible label for a fully active, enabled control risks both a contrast failure and a "this field looks disabled" misread. DESIGN.md has no `search-field` component token at all (no entry under Components). (mockups/key-voyage-history.html lines 46–48, 72–75). *Fix:* add a `search-field` token, raise the placeholder color to `ink-secondary`, and/or give the field a persistent (non-placeholder) accessible label.

- **low** The deck's `.swipehint` text ("← swipe →" / "tap to finish →") renders at `rgba(16,24,40,0.4)`, computing to ~2.4:1 against the aurora — the same class of issue as the first critical finding, but called out separately because it's the *only* textual affordance explaining how to navigate the deck (see the swipe-only finding above); if no non-gestural fallback is added, this hint's low legibility compounds that risk for low-vision users trying to read it. (mockups/key-memory-lane-reveal.html line 48).
