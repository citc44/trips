- (constraint) Non-technical founder: architecture must be fully AI-agent-buildable, self-managed (no manual dev/DB/build/CI-CD steps by the user), low-cost, good-performing - this is the primary driver for every stack choice
- (decision) Working mode: Fast path. Purpose/audience: spine is a build substrate for an AI-driven implementation pipeline (dev agents), not a human-team explainer document - no separate deliverable requested
- (decision) Paradigm: BaaS-centric layered architecture. Mobile client is the only custom-built unit; auth/database/realtime/storage/serverless run on managed Supabase. Client itself layered: screens/features -> shared hooks/services -> repository layer -> Supabase SDK, no screen talks to Supabase SDK directly.
- (version) React Native via Expo SDK 56 (managed workflow) + TypeScript - mobile client, iOS+Android from one codebase
- (version) EAS Build/Submit/Update - fully managed build, app-store submission, and OTA JS update pipeline, no local Xcode/Android Studio/signing needed
- (version) Supabase (Postgres, Auth, Realtime, Storage, Edge Functions/Deno) - sole backend platform. Free tier for early usage (500MB DB, 50k MAU auth, 2M realtime msgs/mo), 5/mo Pro when outgrown
- (version) Mapbox via @rnmapbox/maps - map SDK chosen over stock Google/Apple maps specifically because it supports the custom 'Night Drive' game-like styling the UX spine (DESIGN.md) commits to. Free tier: 25k mobile MAU/mo
- (version) GitHub + GitHub Actions - CI/CD, fully automated pipeline (build/test/deploy via EAS + Supabase migrations) triggered on push, zero manual steps
- (version) Sentry (free tier) - crash/error reporting, since the non-technical founder cannot manually debug, automated error visibility is load-bearing not optional
- (version) Expo Notifications - push notification delivery, integrates natively with EAS
- (decision) AD candidate: Voyage-scoped data access boundary. Binds: all Voyage-related tables (voyage_members, voyage_member_locations, future fun_facts/photos). Prevents: two features independently implementing inconsistent authorization checks in application code, leaking one Voyage's data to non-members. Rule: authorization enforced via Postgres Row-Level Security policies keyed on voyage_members membership, never via application-layer checks alone - matches PRD's hard privacy requirement (data never leaves the Voyage's own Voyagers).
- (decision) AD candidate: single realtime delivery mechanism. Binds: Live Map (FR-9), future Fun Fact notifications (FR-10/11). Prevents: divergent polling/websocket schemes across features. Rule: Supabase Realtime (Postgres change subscriptions + broadcast channels) is the sole mechanism for live/near-real-time delivery to clients.
- (decision) AD candidate: location persistence model. Prevents: naive per-GPS-ping database writes (cost/battery/scale risk). Rule: live position is broadcast ephemerally via Supabase Realtime, NOT persisted per-ping; only a single latest-known-location row per Voyager (voyage_member_locations, upserted) is persisted, for cold-load/reconnect state.
- (decision) AD candidate: single auth session source of truth. Rule: one shared auth context/hook wrapping the Supabase Auth client; no screen manages its own session/token state.
- (decision) AD candidate: repository layer required. Rule: all Supabase queries/mutations go through a per-entity repository module (voyageRepository, memberRepository, etc.); screens/hooks never call the Supabase client SDK directly - keeps query shapes and caching consistent, and gives AI dev agents one obvious place to add new data access.
- (decision) AD candidate: environment separation. Rule: three environments (dev/staging/prod), each a separate Supabase project and a separate EAS build profile; no shared credentials/data across environments.
- (decision) Consistency convention: Postgres UUID primary keys, snake_case DB columns, camelCase client-side mapping, ISO8601 timestamps throughout.
- (decision) Core v1 entities: users (Supabase auth.users), voyages (id, destination, status, created_by, created_at, ended_at), voyage_members (voyage_id, user_id, role[organizer|voyager], joined_at, removed_at nullable), voyage_member_locations (voyage_member_id, lat, lng, updated_at - latest-only, upserted). One voyages row has many voyage_members; each voyage_member has at most one voyage_member_locations row.
- (direction) Deferred: AI content-generation pipeline (Groq confirmed as provider when this feature is scoped - not designed now, feature itself deferred per PRD). Fun Fact Capture + Memory Lane tables/pipeline (v1.1, PRD-deferred). Phone-number OTP. Web companion. Payments/monetization infra. Multi-destination itineraries.
- (event) Spine distilled: BaaS-centric layered paradigm (Expo/RN + Supabase + Mapbox), 6 ADs (RLS data boundary, single realtime mechanism, ephemeral location persistence, single auth session, repository layer, environment separation), core entity ERD, source tree, capability map, Groq confirmed for deferred AI content feature
- (decision) AD candidate: offline resilience. Binds: all Voyage lifecycle writes (start/join/end/grant/remove) and future Fun Fact/photo writes. Prevents: silent failure or corrupted Voyage state when a write is attempted through a cellular dead zone. Rule: client persists a local write-outbox (queued mutations) for any write attempted while offline; outbox flushes and reconciles on reconnect. Addresses PRD Cross-Cutting NFR reliability requirement.
- (decision) AD-4 extended: session revocation resolved via Supabase Auth's native global sign-out (supabase.auth.signOut({scope: 'global'})), which revokes refresh tokens across all devices - closes the PRD's open remote-sign-out item without new infrastructure.
- (decision) AD candidate: background location capability. Rule: client uses expo-location (background permission mode) + expo-task-manager to keep sending location upserts to voyage_member_locations while backgrounded/locked (iOS background location mode, Android foreground service). Backgrounded Voyager's own client does not need an active Realtime subscription to contribute - the upsert write itself triggers Postgres Realtime broadcast to other connected clients.
- (decision) Entity model addition: profiles table (user_id PK/FK to auth.users, trust_moment_seen_at, driver_consent_seen_at) to make the Trust Moment and Driver Attention Consent 'once ever' PRD/UX requirement enforceable server-side.
- (decision) AD candidate: one active Voyage per user. Rule: a partial unique constraint/check ensures a user has at most one non-removed voyage_members row on an active Voyage at a time, enforcing EXPERIENCE.md's foundational 'one active Voyage at a time' assumption in the data model, not just client logic.
- (decision) Entity model addition: push_tokens table (user_id, expo_push_token, updated_at) plus a Supabase Edge Function as the notification dispatch path. Operational note: iOS Time-Sensitive notification entitlement requires a manual one-time Apple Developer Program request/approval - the one step in this whole architecture that is NOT purely code/AI-automatable, since it's an Apple administrative approval, not a technical build step.
