# Story 4.4: Reskin Epic 1 & 2 Screens

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Voyager,
I want every screen — not just Live Map — to use the new colorful design system,
so that the app feels consistent app-wide instead of having one redesigned screen surrounded by the old dark/glass look.

## Acceptance Criteria

1. **Given** Story 4.1's new design system, **when** I use OTP Sign-In/Verify, Trust Moment, Driver Attention Consent, Home, Voyage Intro, Destination Picker, Join Invitation, or Voyage Ended, **then** each screen renders using the new Wayfinder palette and components, with no remaining Night Drive dark/glass styling.
2. **And** no flow, copy, or logic changes are introduced — this is a visual re-skin only.
3. **And** screen-to-screen navigation within this set uses Story 4.1's specified transition types/timing (`EXPERIENCE.md`'s "Standard push"), not default platform transitions or instant cuts.
4. **And** each built screen matches its linked mockup exactly (colors, spacing, radii, component treatment) — verified side-by-side against the mockup file during code review, not approved on "close enough."

*(Fulfills app-wide scope of Story 4.1's design output across Epics 1-2's screens.)*

## Scope decision (read this before writing any code)

This story touches 8 screens plus one shared button component and one new shared decorative component. Several of the mockups contain content that isn't purely visual — read this section fully before starting; it resolves every case where "match the mockup exactly" (AC #4) and "no flow/copy/logic changes" (AC #2) could otherwise pull in different directions. Where the two conflict, **AC #2 wins on *what* the screen shows or does; AC #4 wins on *how it looks*** — the same precedence `EXPERIENCE.md` itself states ("where a mockup and this document ever disagree on *what* a screen does, this document wins. On *how it looks*, mockup-fidelity is a hard requirement").

**Trust Moment / Driver Attention Consent are not light screens — this is correct, not a mockup bug.** Both mockups (`key-trust-moment.html`, `key-driver-consent.html`) show a full-bleed dark `#101828` canvas, not a white/fog Wayfinder canvas. This matches `DESIGN.md` exactly: `surface-ink-navy` (`#101828`) is documented as "the one deliberate exception to 'no dark surfaces'... reserved exclusively for the two onboarding consent moments." Re-skin these two screens *to* `surface-ink-navy` + `ink-on-navy-primary`/`ink-on-navy-secondary` (new Wayfinder tokens, not yet in `design-tokens.ts` — see Task 1), not away from dark.

**Voyage Intro / Join Invitation are full-bleed `accent-primary` blue, with an inverse (white-fill) button — also correct, not a bug.** Both mockups show solid `#0B6FFF` canvases with a white pill button (`background:#fff; color:#0B6FFF`). `DESIGN.md` names this explicitly: "the app's biggest emotional beat, and the one screen allowed to fill the frame with `accent-primary` itself... `button-ignition-inverse` (white fill, blue label) since a solid-primary button would vanish on a solid-primary field." `button-ignition-inverse` is a real, already-specified `DESIGN.md` token (frontmatter `components.button-ignition-inverse`: `background: '#FFFFFF'`, `foreground: '{colors.accent-primary}'`, `radius: full`, `minHeight: 56px`) — add it to `design-tokens.ts` (Task 1) and give `ignition-button.tsx` a new `variant="inverse"`.

**Home (`index.tsx`) has two real behaviors the mockup doesn't show — keep both, re-skin both.** `key-home.html` shows only a wordmark and one "Start a Voyage" button. The actual screen also has a `join-voyage-button` (routes to `/join`) and a `settings-link` (routes to `/settings`), both asserted by `index.test.tsx`. Per AC #2, do not remove either — the mockup is visually incomplete for this screen, not a spec for a reduced feature set. Re-skin all three elements to Wayfinder tokens; use the mockup's one visible button as the literal reference for the primary button's treatment, and use `button-secondary`/a plain text-link treatment (whichever reads better against the fog canvas) for Join/Settings, inferred consistently with how other screens treat secondary/tertiary actions.

**Join Invitation's personalized eyebrow ("Chintan invited you") and 3-avatar stack are new content/logic, not just visual polish — do not add them.** `key-join-invitation.html` shows a real inviter name and per-Voyager colored avatar initials. The current `join/[code].tsx` deliberately does not implement this yet (its own code comment says so) — it shows a generic Voyager-count line and a trust-line reassurance box instead, neither of which appears in the mockup. Keep the current generic-count + trust-line structure and *re-skin its colors/spacing/typography* to the mockup's blue-hero treatment (eyebrow color, headline/subhead size, `button-ignition-inverse`) — do not build inviter-name personalization or an avatar stack; that's new product logic requiring new data, out of a re-skin story's scope.

**Voyage Ended's mockup restructures the summary from one flat sentence into a card with separate labeled stat chips — this is a visual restructuring, not a copy change, and is explicitly sanctioned by `DESIGN.md`'s own `card` token doc** ("Voyage Ended's summary panel" is named directly as one of `card`'s intended use sites). Implement the mockup's structure: an icon badge, a `card`-token container, a "Destination" label + value, and a horizontal-rule-divided stat row with "Duration"/"Voyagers" as separate labeled `stat-numeral`-styled values. Keep the exact same underlying information and per-segment wording the current screen already has (do not invent new copy) — but the existing test's single combined-string assertion (`getByText('5h 30m · 3 Voyagers · Lake Tahoe')`) will need to become multiple, per-segment assertions matching the new structure; that's an expected, sanctioned test adaptation, the same class of change Story 4.3's own hud-top/hud-bottom restructuring required. Keep the existing headline text **"Voyage ended."** unchanged (a real, protected copy string per AC #2) even though the mockup's own placeholder text reads "Voyage complete" — the mockup wins on structure/colors/spacing here, not on this one string.

**OTP's code-box count stays at 8, not the mockup's visual 6.** `key-otp-signin.html`'s `.code-row` shows 6 `.code-box` elements and copy reading "6-digit code" — but `CODE_LENGTH = 8` in `sign-in.tsx` is a real, load-bearing business-logic constant matching `supabase/config.toml`'s `[auth.email] otp_length = 8` (verified directly against the config file — the file's other `otp_length = 6` entry is under the unrelated `[auth.mfa.phone]` section, not used by this app's email-OTP sign-in flow at all). Render 8 boxes using the mockup's exact `.code-box` visual treatment (size, radius, border, active/filled states), not 6. This is a mockup authoring inaccuracy, not a spec to follow — AC #2's "no logic changes" protects the real digit count.

**OTP/Destination Picker's back-arrow: restyle what exists, don't add new navigation.** Both mockups show a `.back-arrow` icon button (38×38px, top-left) on every step shown. `sign-in.tsx`'s *verify* step already has an equivalent, tested control (`back-to-entry`, currently a text-link-styled `IgnitionButton` reading "Wrong email? Go back") — restyle that one to the mockup's icon-arrow treatment (keep the same `testID`/`onPress`, add `accessibilityLabel="Wrong email? Go back"` so the meaning survives the icon-only visual). `sign-in.tsx`'s *entry* step and `destination-picker.tsx` have **no existing back control at all** — do not add one; that would be new navigation behavior AC #2 doesn't authorize. Their headlines/inputs still get the mockup's other styling (typography, input treatment, horizon-strip); the mockup's back-arrow simply isn't built on those two steps in this story.

**Destination Picker's input `.filled` state (border turns `accent-primary` once text is entered) is new interactive polish, not existing behavior — safe to add, purely visual.** Unlike the back-arrows above, this doesn't change any flow/logic — it's a conditional style keyed off already-existing state (`selectedPlace`/text presence), the same category of addition Story 4.2 made for the drawer's footer tagline ("cheap and unambiguous to add given the fidelity mandate"). Include it.

**Destination Picker's current eyebrow+headline two-line treatment ("Destination" / "Where are you headed?") collapses to one line in the mockup** (only "Where are you headed?" as the headline; "Destination" only appears as the input's own field-label, not a separate page eyebrow). This is a visual layout change, not a copy or logic change — both strings survive, just restructured. Follow the mockup: drop the standalone eyebrow, keep "Destination" as the field's own label above the input.
