## Deferred from: code review of story-2-1-start-a-voyage (2026-07-27)

- **`is_active_voyage_member` remains callable directly by any *authenticated* user as a narrow membership-existence oracle for arbitrary `(voyage_id, user_id)` pairs.** An attacker needs to already know both UUIDs (neither is enumerable), but a malicious existing member probing a known acquaintance's user id against a known voyage id is a real, if narrow, scenario. Public/anonymous access is already closed (this story's code review added an explicit `revoke ... from public`). Fully closing the authenticated-user angle means moving the function to a schema PostgREST doesn't expose — a structural precedent decision affecting every future Voyage-scoped RLS policy, since this function is the explicit template Epic 2/3 are told to reuse, not a quick fix to make unilaterally.
- **`voyages_select_members`/`voyage_members_select_fellow_members` route entirely through `is_active_voyage_member`, which requires `v.status = 'active'` — once a future "End Voyage" story flips `status` to `'ended'`, every SELECT policy on both tables will deny access to everyone, including the former organizer, with no historical-read predicate.** No voyage can reach `status = 'ended'` yet (Story 2.4's job). Designing the "who can read an ended voyage" predicate belongs with that story, once its actual requirements (plus Memory Lane v1.1's eventual read needs) are known — guessing now risks over-engineering.
- **No automated regression test (e.g. pgTAP) exists for either of the two real RLS pitfalls live verification found in Story 2.1** (a RETURNING-clause-requires-the-SELECT-policy ordering issue, and `security invoker` self-recursion in a membership-predicate function called from its own table's policy). This project has no SQL-level test infrastructure at all yet; building it is a dedicated investment decision. Both pitfalls are now documented in the relevant migration files' comments as a stopgap.

## Deferred from: code review of story-3-5-connectivity-loss-reconnection (2026-08-01)

- **No dedup of duplicate offline-outbox items.** Re-tapping End Voyage/Grant Organizer/Remove Voyager after an earlier attempt already queued (e.g. the user isn't sure the first tap registered) produces two queue entries for the same operation. On flush, the second (redundant) attempt legitimately fails with a real conflict errcode, surfacing a confusing "conflict" toast for an action the user already believes succeeded — not data-corrupting (the underlying write only ever happens once), but confusing. A proper fix needs a dedup key (kind + voyageId + targetUserId) and matching semantics not yet designed.
- **The offline outbox's network-failure-vs-conflict classifier (`error.code === 'unknown'`) would misclassify `endVoyage()`'s own synthetic `{code: 'unknown', message: 'Failed to end Voyage.'}` fallback** (its defensive guard against a malformed RPC response) as a network failure, queuing and retrying it forever instead of surfacing it as a real error. Highly defensive-only path — the RPC's own `select ... into strict` guard should prevent this server-side — so low reachability, but worth a distinct signal if this fallback is ever seen to actually fire.
- **`subscribeToLocations`'s `CHANNEL_ERROR` status is treated identically whether the cause is transient (a real connectivity drop) or permanent (e.g. an auth/RLS rejection)**, so the "Reconnecting…" HUD note would show forever for a non-recoverable failure with no escalation. Genuinely uncertain without live Realtime testing — no clear client-side signal exists today to distinguish the two cases.
