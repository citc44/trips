## Deferred from: code review of story-1-1-project-foundation-environments (2026-07-26)

- **AC #4 prod pipeline never actually executed.** `.github/workflows/prod-deploy.yml` is written and structurally identical to the verified dev workflow, but its first real `workflow_dispatch` run was explicitly deferred by user choice until an actual prod release is wanted.
- **`scripts/reset-project.js` self-delete-on-Windows / silent-catch-and-exit-0 issues.** Unmodified Expo boilerplate (deletes its own containing directory on Windows if the user answers "n"; swallows errors from `moveDirectories` and exits 0 anyway). Not exercised by the app or CI — only run once, manually, by a human who no longer needs the sample screens.
- **`eas build --no-wait` means CI green only proves the build was queued, not that it succeeded.** Both promotion workflows fire-and-forget EAS builds. Waiting in CI would add real time/cost; the accepted tradeoff is that build success must be checked separately (Expo dashboard) rather than inferred from workflow status.
- **`eas.json`'s CLI version constraint (`>= 21.2.0`) has no upper bound.** Generated by `eas build:configure`'s own default; any future major `eas-cli` release could be picked up silently in CI.
- **`predictiveBackGestureEnabled: false` in `app.json` is undocumented.** Inherited from Expo's default scaffold template, not a deliberate product decision — worth revisiting once the app actually has Android back-gesture UX to consider.

## Deferred from: code review of story-1-2-email-otp-sign-in (2026-07-26)

- **🚫 RELEASE BLOCKER: no real user other than the Resend account owner can currently receive an OTP email.** `supabase/functions/send-otp-email/index.ts` sends from `onboarding@resend.dev`, Resend's shared test domain — confirmed via Resend's own docs, this domain can only deliver to the email address associated with the Resend account (i.e., only `citc_44@hotmail.com` right now). Any other real user signing up would silently receive nothing, even though the request returns HTTP 200. **Must verify a real Voylo domain in Resend before any testing or usage involving anyone but the developer.** Accepted as not-yet-urgent since no domain is registered yet, but this is a hard blocker, not a cosmetic branding gap.
- **`getSession()` and `onAuthStateChange`'s `INITIAL_SESSION` event both fire on mount, unordered.** Verified this is Supabase's own documented pattern (both calls are meant to coexist), and both read the same underlying session storage, so the theoretical race doesn't produce practically different values — not a real bug, just a shape worth knowing about if a genuine sign-in race is ever suspected later.

## Deferred from: code review of story-1-3-persistent-session-sign-out (2026-07-26)

- **Two parallel theming systems in active use.** `src/app/index.tsx` still uses the Story 1.1-era `ThemedText`/`ThemedView`/`@/constants/theme` (follows OS light/dark via `useColorScheme`), while `src/app/settings.tsx` and `src/app/sign-in.tsx` use `@/constants/design-tokens`'s hardcoded dark "Night Drive" palette. A user in light mode sees Home rendered light, then gets snapped into a forced-dark screen on Sign-in/Settings. Resolve when Home gets its real DESIGN.md-driven redesign (Epic 2's "Start a Voyage" work) — migrate Home onto `design-tokens.ts` at that point rather than patching it in isolation now.
- **No automated end-to-end test for actual Supabase token revocation** — only a unit-level assertion that `signOut` is called with `{ scope: 'global' }`. The real revocation guarantee was proven manually (two-session `curl` round-trip against live `voylo-dev`, Story 1.3's Task 5) but leaves no regression-catching artifact in the repo. Consistent with this project's deliberate convention of live manual verification over committing live-credential E2E tests to CI; revisit if a dedicated test-Supabase-project/secrets setup is ever built.
- **Text-based "disabled" buttons (`onPress` nulled, no true native `disabled` prop) may not announce correctly to screen readers.** Pattern originates in `sign-in.tsx`'s secondary-button variant (Story 1.2), now duplicated into `settings.tsx`. Worth a dedicated accessibility pass across all button variants at once rather than fixing piecemeal per screen — matches EXPERIENCE.md's "Accessibility floor" requirement (VoiceOver/TalkBack announcements on every interactive element).
