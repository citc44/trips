# Story 6.3: Build End-of-Voyage Memory Lane Reveal

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Voyager,
I want ending a Voyage to reveal a beautiful, animated recap of the trip,
so that finishing a Voyage feels like a reward, not just closing out a tracker.

## Acceptance Criteria

1. **Given** Story 6.1's data foundation and Story 6.2's approved spec and mockups **When** an Organizer ends the Voyage (FR-6) **Then** a versioned, deterministic (template-based, no AI) composer assembles the Memory Lane immediately from data that actually exists today: opening title/destination/date/participating Voyagers, who-joined-when for each Voyager, actual trip duration, and journey events already captured by Story 5.1 (police/deer/construction spottings) — with a complete, non-empty recap even when zero Fun Facts/photos exist.
   - **Scope amendment (exhaustive-analysis finding, confirmed with user):** epics.md's original AC1 also named "Planned-vs-Actual travel time," "distance and time traveled together," and "states/countries crossed." None of these are computable with data that exists in this schema today — `voyage_member_locations` holds only each Voyager's single *latest* position, never a route/trail history, and there is no destination-ETA/route-planning capture anywhere to give "planned" time a value to compare against. Per user decision, this story scopes the composer to what real data supports and explicitly defers distance/route/state-crossing/planned-time as a documented gap for a future story (new location-trail capture), not a silent omission. See Dev Notes → "Data gap: no route/trail data."
2. **And** the reveal plays Story 6.2's spec'd animation exactly, verified side-by-side against `mockups/key-memory-lane-reveal.html`, not approved on "close enough" — including the one intentional pixel deviation from that mockup covered by AC1's scope amendment (see Dev Notes → "Finale card deviates from its mockup").
3. **And** Memory Lane generation is idempotent — re-opening or a retried assembly never produces a duplicate or a different result for the same Voyage. (Architecturally satisfied by computing the recap as a pure, read-only projection over existing durable `journey_events`/`voyages`/`voyage_members` rows on every view — see AD-17 — rather than writing a new stored "generated recap" artifact; nothing is created, so nothing can duplicate.)
4. **And** every participating Voyager can independently view the same Memory Lane from their own app (FR-15), and revisit it later, not just at the moment of the reveal — satisfied by the deck being a route reachable by `voyageId`, independent of the End-Voyage transition that first triggers it (Story 6.4 will later link a Voyage History row to this same route; this story does not build that list).
5. **And** a solo (unjoined) Voyage still produces a complete Memory Lane — never a degraded "not enough people" state.
6. **[NEW, scope decision confirmed with user]** Closing the reveal deck lands on a minimal Persistent Journey Screen (`journey-screen` token) — destination, crew avatar stack, a replay control that re-opens the deck from the start, and a stat summary (duration + stop count; no distance, per AC1's scope amendment). This is the deck's required landing target per `EXPERIENCE.md`'s IA ("the closing beat... always lands on the Persistent Journey Screen") — the deck cannot ship without somewhere to close to.
7. **[NEW, scope decision confirmed with user]** The Persistent Journey Screen's "Share the card" control generates the single `memory-lane-share-card` image (quote-led direction, confirmed in Story 6.2) from the same composer data and opens the OS share sheet.
8. **[DEFERRED during implementation — confirmed with user; see Dev Notes → "AC8 deferred: video sharing"]** ~~The Persistent Journey Screen's "Share the video" control stitches the 5 reveal cards into an MP4 with transitions and opens the OS share sheet.~~ Not built in this story. `ffmpeg-kit-react-native` (the candidate identified during Story 6.2's UX discovery) turned out to be officially discontinued, and exhaustive research during this story's implementation found no actively-maintained on-device alternative capable of composing a still-image sequence into a video for React Native/Expo today. The viable path is server-side/cloud video generation — a real new-backend-infrastructure decision, not a dependency swap — which the user explicitly chose to scope as a separate follow-up story rather than decide under this story's time pressure. Task 7 (the still-image share card) ships in this story.

## Dev Notes

### Data gap: no route/trail data

`voyage_member_locations` (the only location-history-adjacent table in this schema) is written by the live-tracking pipeline and read gated on `is_active_voyage_member` — it holds each Voyager's single *latest* position only, overwritten on every update, never a trail. There is no other location-history table anywhere. Story 6.1's own Dev Notes explicitly flagged this exact gap forward to this story rather than attempting a fix. Per user decision (this story's exhaustive-analysis pass), distance-traveled, states/countries-crossed, and "planned vs. actual" travel time are **out of scope for this story** — the composer (Task 1) must not attempt to synthesize or estimate these from data that doesn't support them. A future story would need new location-trail capture (a genuinely new data-collection concern, not a query/access-control fix) before these fields could be added.

### Distance stat omitted throughout — 3 places to reconcile

The distance data gap (no route/trail table exists) surfaces in three places across the finalized UX spec, all written before this story's exhaustive-analysis pass discovered the gap. All three need the same fix — duration + stop-count, no distance — for consistency:

1. `mockups/key-memory-lane-reveal.html`'s finale card shows a Duration + Distance pair (`6h 42m` / `214mi`).
2. `mockups/key-memory-lane-share-card.html`'s hero stat pair shows the same Duration + Distance pair.

### Shareable card: no consent gate for other Voyagers (v1 decision)

The shareable Memory Lane card (Task 7) renders every Voyager's display name, initials, and player color — not just the sharer's own — with no per-Voyager opt-out or consent prompt before the image can leave the app. This was flagged in this story's code review (2026-08-21) as an unreviewed decision (the original comment cited "per Dev Notes" for a decision this file never actually made). Resolved by user decision: **accept this behavior for v1.** Rationale — every Voyager on a trip can already see every other Voyager's display name, initials, and player color live in-app for the whole trip (roster, map markers, peek cards); the shareable card doesn't expose anything a fellow Voyager didn't already have visibility into, it just externalizes data that was never private *among the group* in the first place. A consent gate or anonymize-others option is a real, separate feature (e.g. for a Voyager who doesn't want their name leaving the app in someone else's share) and can be scoped as its own story if it comes up.

### Offline/network-failure pattern (follow exactly, where it actually applies)

Every existing write-triggering handler in `active-voyage.tsx` (`handleEndVoyage`, `handleGrantOrganizer`, `handleRemoveVoyager`, Story 5.1's `handleLogSpotting`) follows the same shape: try the repository call directly; on `isNetworkFailure`, call `outbox.enqueue(...)` explicitly from the UI handler (not inside the repository function). This story's own writes are read-heavy (the composer never writes), so the offline-queue half of this pattern mostly doesn't apply here.

The **ref-based re-entrancy guard** half does apply directly to Tasks 7-8's share-generation flows (tapping Share twice while a video is still stitching must not start a second stitch — state-only guards read stale within the same React batch, a real bug already fixed once during Story 5.1, don't reintroduce it here). But `isNetworkFailure`/`outbox.enqueue` itself does not map cleanly onto image capture or video stitching — both are local, network-independent operations once composer data is already loaded (no Supabase RPC in that step). Handle their actual failure modes instead: a native-module error, device storage full, or a share-sheet/file-permission denial — a plain inline retry per the State Patterns spec, not an offline-queue retry (there's nothing to reconcile on reconnect; a failed local render should just be retried).
